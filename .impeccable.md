## Design Context

### Status and decision

**Status: approved.** On 2026-09-21 the owner chose **A — Planning studio (Recommended)** after viewing two rendered directions. No further rationale was supplied; do not invent one.

Scope: the Rosette pilot applies A to the existing upload → analysis → room review → placement → calculation → results/export journey. The concept's fictional routines/notes are not backend features and must not be implemented as if they were.

### Users

Confirmed primary audience: homeowners planning a renovation. An electrician reviews the result. Desktop supports focused planning; mobile must support readable review, error recovery, and the same core actions.

### Brand personality

Considered, domestic, conversational. Help a homeowner understand the next step without intimidating CAD-like density or implying that generated material is an approved electrical design.

### Aesthetic direction

Selected: [A, the planning studio](docs/design-directions/studio.html). [B, the spatial workbench](docs/design-directions/workbench.html) remains exploration history, not an alternative theme.

Use warm plaster `#f4f0e7`, paper `#fffdf8`, walnut ink `#302f28`, olive `#4e603b`, sage `#e6ebd8`, and readable stone `#666255`. Pair locally available Georgia display type with Segoe UI/Tahoma body text. No downloaded font, branded asset, or new component framework.

Signature: a paper-like plan beside clear room decisions, framed by restrained editorial typography. The actual uploaded plan—not a fabricated sample—belongs at the centre of the real journey. Motion is optional; waiting states describe real work without fabricated progress.

### Design principles

1. Put the homeowner's plan and room names before technical detail.
2. Keep every country, language, standards view, and export available.
3. Preserve entered work when requests fail; make retry an explicit action.
4. Use visible native keyboard controls, legible mobile text, and clear focus.
5. Present results as a planning aid for qualified electrician review, never approval.

### Primary journey and states

Choose a floor-plan file and property/country → analyze → review/add/remove rooms and adjust requested counts → place/edit sockets and board → calculate → inspect diagrams and English/local specification → download existing formats.

Exercise first use, selected file, genuine waiting, empty analysis, network error/retry, edited room data, failed calculation with retained placement, complete results, long names/specifications, and export. Do not replace service failures with synthetic success in production.

### Constraints and verification

Existing APIs, models, electrical calculations/standards, authentication, storage, payment behavior, and deployment remain unchanged. Browser tests intercept services with clearly labelled synthetic API-shaped fixtures; never use private plans or live credentials.

Target WCAG 2.2 AA; inspect keyboard/focus, contrast, labels, reduced motion, narrow layouts, and 200% text enlargement. Representative captures: 390 × 844 and 1440 × 1080 CSS pixels; also inspect 320 and 768 widths.

Pilot performance budget (implementation proposal, not an owner-specified SLA): no external font requests, no new production dependency, no eager loading of the existing placement/PDF/markdown chunks. Record the actual production build sizes and local browser measurements; do not claim field Core Web Vitals or an unmeasured Lighthouse score.

Source-bound PNGs, task observations, actual test commands, and independent review live under `docs/design-evidence/planning-studio`. A receipt cannot pass before independent review is complete.
